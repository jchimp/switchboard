Status rules

How the manager decides what each segment means. WT doesn't publish activity, so status is inferred from things the manager can observe from outside the window.

Working

Title matches a busy pattern, or output is still scrolling.

Attention

Bell, a "done"/"waiting" title, or the window flashed. Pulses until focused.

Idle

Prompt visible, nothing for 20 s.

Closed

No window found. Segment dims; click launches.

Window title changes

WinEvent hook on EVENT_OBJECT_NAMECHANGE. Cheapest signal, and your shells already set titles — Claude Code, pwsh prompts, vite, and htop all do. Per-terminal regexes map titles to states.

Taskbar flash

EVENT_OBJECT_SHOW/flash detection — catches BEL from any shell without you configuring anything.

Thumbnail motion

Diff the DWM thumbnail every second; changing pixels = working. Catches long builds that never touch the title.

Named pipe from the shell

Opt-in: a one-line hook in your PowerShell profile or .bashrc writes state=attention to \\.\pipe\termmux. Exact, but needs setup per shell.

What lives in registry.json

Name, tag, color, WT profile, working directory, an optional startup command, the jump key, and the status rules. That file is the whole product state — easy to back up, diff, and hand-edit.

How a row becomes a window

wt -w anvil new-tab -p "Ubuntu" -d ~/anvil --title "anvil" --tabColor "#b07cf5" -- claude --resume. The manager then finds the HWND by class + title, stores it, and applies the frame color.

Why status is its own section

The strip is only worth having if "something changed" is reliable. Title hooks and thumbnail motion give you that with zero shell config; the pipe is the precision upgrade when you want it.
